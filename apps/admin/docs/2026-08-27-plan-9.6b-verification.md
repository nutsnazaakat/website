## What the live run actually did

Signed in **once** as `admin@demo.in` and reused the session for everything below.
`POST /auth/login` is 5 per 15 minutes per IP, and a script that signed in per case rate-limits
itself and reports failures that look like application bugs.

### Reads — money is rupees, everywhere

`totalSpend: 77348.25`, `flatValue: 500`, `minOrderValue: 10000`, `expectedValue: 84500`. Not one
figure needed converting, and nothing in this app calls `toRupees` on a response. Plan 9.6a's own
text said "paise" and was wrong; that correction held for all nine of Group B's screens.

Three claims the screens make were checked against the running service rather than assumed:

- **Approving a review is not a display flag.** `premium-california-almonds` read `ratingAvg 3.67`
  over 3 reviews; approving a 5-star review moved it to `4.0` over 4, and rejecting the same row
  moved it back to `3.67` over 3. The reviews screen says so under the queue.
- **A reopened ticket has no resolution date.** Resolving stamped `resolvedAt`; moving back to
  `open` set it to `null`. That is the opposite of the blog's stamp-once `publishedAt`, and the
  triage panel spells out the difference.
- **Stock movements really are absent from the audit log.** Two threshold changes produced two
  `inventory.update` audit rows and no ledger rows; two stock adjustments produced two ledger rows
  (`delta 1 -> 41`, `delta -1 -> 40`) and no audit rows. The audit screen's notice is accurate, and
  the distinction it draws — *if stock moved, it is in the ledger* — is exactly what the service does.

## What Group B settled

- **Money is rupees**, confirmed again on nine more screens. Nothing converts.
- **A path with children gets a directory.** `rfqs/index.tsx` + `rfqs/$rfqNumber.tsx`, and no
  `rfqs.tsx` beside them; likewise customers, businesses and support.
- **`search.strict` is on**, so a hand-edited parameter no route declared is dropped before it can
  reach a `forbidNonWhitelisted` endpoint and earn an uninterpretable 400. Pinned by a test that
  hand-edits `?role=admin&bogus=1` and asserts neither reaches the wire.
- **Search boxes are uncontrolled, keyed on the applied term, and applied on blur or Enter.** Group
  A settled that shape on `/products`; Group B adopted it rather than introducing a second one, so
  every list in the console behaves the same way. A controlled box re-synced by an effect renders
  once with the stale text and again with the fresh one.
- **Refusals are rendered, not swallowed.** Four different ones now have screen text behind them:
  the coupon `409 ENTITY_IN_USE` with its redemption count, the RFQ `422` with its `allowed` list,
  the settings `404` naming the unknown key, and the blog `409` on a taken slug.
- **Where an endpoint does not exist, the screen says so instead of offering a control.**

## Where the plan, the spec and the API turned out wrong

- **`PATCH /admin/businesses/:id` does not exist.** Spec §6.4 lists it; nothing implements it. Plan
  9.3 recorded the gap and 9.6b's task B2 repeats it. `/businesses/$id` therefore shows `segment`
  and `assignedSalespersonId` as facts under a padlock, and a route test asserts there is no input
  in that panel — because an input answering 404 teaches an operator the console is broken, which
  is a worse outcome than a missing feature.
- **Nothing enumerates operator accounts.** A salesperson is an admin *user*, and
  `GET /admin/customers` deliberately excludes admins — its `role` filter is `b2c|b2b` and the
  service filters `role <> 'ADMIN'` regardless. There is no `GET /admin/salespeople` and §6.4 never
  specified one. So `/rfqs/$rfqNumber` and `/support/$ticketNumber` can offer only "assign to me"
  and "unassign", and another operator's assignment renders as *assigned* with no name, because the
  wire carries a uuid and nothing resolves it. **This is the one gap worth an endpoint.**
- **There is no single-item read for a coupon or an admin post.** `/admin/coupons` and
  `/admin/posts` have list, create, patch and delete, and no `GET /:code` / `GET /:slug` — and the
  public post route only serves *published* ones, so it cannot open a draft. Both screens are
  therefore a list with an inline editor rather than a list and a detail route, and both say so when
  `?edit=` names a row on another page.
- **`GET /admin/reviews` cannot return every status.** It always filters on exactly one and defaults
  to `pending`, so the screen offers three real choices and no "All" — an option that sent nothing
  would show pending rows under a label promising everything.
- **`AdminSupportTicketsService.list`'s docblock is out of date.** It says the desk "uses `?status=`
  and `?priority` to find the rest"; `AdminSupportTicketQueryDto` declares no `priority` parameter,
  and `forbidNonWhitelisted` would answer 400 rather than ignore it. A comment fix in the backend,
  not a code one.
- **`PATCH /admin/inventory/:variantId` returns `{onHand, balanceAfter}` and nothing else** — the
  two identical by construction — unlike its `/threshold` twin, which returns the whole re-read row.
  Found by Group A, confirmed here. Not fixed; recorded so nothing assumes a write hands back a
  complete row.
- **§7.1's "eighteen routes" is a count of what §7.1 named, not of what the console has.** See
  above. `CONSOLE_ROUTE_COUNT` now carries that distinction in a docblock so the two are not
  conflated again.

## Two follow-ups, deliberately not done here

- **`errorMessage` should move to `src/lib/`.** It lives in `features/orders/api/errors.ts` because
  9.6a put it there, and it is entirely generic — 429 carries no code, 403 must not read as "signed
  out", everything else passes the server's own sentence through. Every feature imports it from
  orders, which reads oddly. It was left alone rather than moved while a second plan was editing the
  same files; a second copy would have been worse than an odd import.
- **Five lists still inline their pagination.** `components/pager.tsx` exists and Group B's seven
  lists use it; orders and the four catalogue screens were written on a parallel branch and were
  left alone. Converting them is a tidy-up worth doing on purpose.
