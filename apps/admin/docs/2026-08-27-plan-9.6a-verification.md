## Where the plan, spec or brief was wrong

### 1. "Money is paise on the wire" — wrong, and it would have been a 100× bug

The task framing said money is paise and to use the contract's conversion helpers. It is **rupees**.
Spec §8 converts at the mapper boundary; the contract's `types/admin.ts` header says "**Money is
rupees**, per spec §8"; `AdminOrderSummary.total`'s docblock says "GST-inclusive rupees"; and the
running service returns `total: 1020.85` and `totalSales: 83492.55`.

Calling `toRupees` on those would have divided by a hundred a second time. The admin console design
spec's §5 bullet "**Money stays in paise**, per §8" is about backend storage and reads as the
opposite out of context — that is probably where the framing came from.

### 2. `search.strict` defaults to `false` in TanStack Router

Not in the plan, and it defeats `validateSearch` in exactly the way that matters here. A route's
validator can only *add* to the query string, never remove from it, so `/orders?status=nonsense`
reached `GET /admin/orders` verbatim — and the backend's global `ValidationPipe` runs with
`forbidNonWhitelisted`, so that is a 400 rather than an ignored filter. Measured, not assumed:
the match's search still carried `status` and a `bogus=1` no route had ever declared.

Fixed with `search: { strict: true }` on the router, pinned by a test.

### 3. The scaffold was missing `"strict": true`

`tsconfig.app.json` had no `strict`, while `nutwala-client`'s does. Without `strictNullChecks` every
`| null` in the vendored contract — `customer.userId`, `paymentCollectedAt`, `OrderLine.total` — was
being erased, and without `noImplicitAny` an inferred `any` spreads while a ban on the *word* `any`
still appears to hold. Also missing: the `@/*` path alias that `vite.config.ts` already declared,
and any `.prettierrc` despite a `format:check` script and `prettier-plugin-tailwindcss` installed.
All three added.

### 4. The vendored contract was stale on arrival

`npm run contract:check` failed at `4cac6b07`: four backend commits had changed `shared/src` since,
including plan 9.4's business timezone. Synced to `7638b3f9`. Nothing this plan depends on changed
shape — the additions were plans 9.3/9.4's new admin types.

### 5. `GET /admin/orders` has no search parameter

Not a plan error, but the first control an operator reaches for, and inventing one is a 400 rather
than an ignored filter. The screen says so out loud rather than omitting it silently.

## Judgment calls

- **Commits 2, 3 and 4 of the plan are one commit.** The route guard *is* the layout route and the
  layout's only child path is `/`, which is the dashboard. Splitting them meant two commits that do
  not build plus a placeholder screen written only to be deleted. Task 5's orders subtree does
  separate cleanly and is its own commit.
- **The route parameter is `$orderNumber`, not §7.1's `$id`.** Same path; `AdminOrder.id` *is* the
  order number, and `$id` invites the next reader to pass a uuid into a route with no
  `ParseUUIDPipe` behind it.
- **No charting library.** `recharts` renders nothing measurable in jsdom (`ResponsiveContainer`
  measures 0×0), so a dashboard test could only have asserted a container exists — the exact failure
  this plan warns about. Three of the four charts are ranked-magnitude comparisons that read better
  as dense CSS bars anyway.
- **Native `<select>` over a Radix listbox.** No radix package is installed here. The native control
  is keyboard-native, portal-free, type-to-select, and drivable in a real route test.
- **`noUncheckedIndexedAccess` on**, beyond the storefront's settings. This app indexes arrays
  straight off API responses and an empty one is an ordinary answer.
- **`only-export-components` disabled for `src/routes/**`** only. Every TanStack route file must
  export `Route` beside its component; that is the framework's contract, not a mistake. The two
  genuine warnings elsewhere were left visible, and one was fixed by dropping an unused export.
- **A `backend/.env` was created** to run the service. It is gitignored, so `nutwala-backend`'s
  tracked tree is untouched — `git status` there is clean. `CORS_ORIGINS` gained
  `http://localhost:5174`.
- **`dateTime` formats in the browser's timezone.** Plan 9.4's business timezone applies to *bucketed
  calendar days* — `salesOverTime.date` and `?from`/`?to` — and this app never re-derives those
  (`businessDay` splits the string rather than building a `Date`, because `new Date("2026-08-21")` is
  midnight UTC). An order's `placedAt` is an unbucketed instant, so formatting it locally undoes
  nothing.

## Notes for 9.6b

- **`POST /auth/login` is throttled at 5 per 15 minutes per IP.** A live suite that signs in per
  case rate-limits itself on the second run and reports failures that look like application bugs.
  `live.integration.tsx` signs in exactly twice and shares the session. The throttler's storage is
  in-memory, so restarting the backend clears it.
- **`POST /admin/orders/:orderNumber/shipment` also transitions the order to `shipped`**, transition
  first, so an order that cannot legally reach `shipped` is refused and no shipment row is written.
  It therefore **cannot record a second dispatch or attach a late AWB**, and there is no
  `PATCH /admin/shipments/:id`. The screen says so; a later plan may want the route.
- **`ILLEGAL_STATUS_TRANSITION` is emitted at both 422 and 409.** `details.allowed` exists only on
  the 422. Branch on status, not on `code` alone.
- **All admin writes answer 200, never 201** — shipment creation included, though it creates a row.
- `PATCH /admin/businesses/:id` still does not exist, so `businesses.segment` and
  `assigned_salesperson_id` have no writer. Unchanged from the plan's own "Known gap".
